# Music, Photos and Other Videos — frontend implementation

Approved scope: 2026-10-09, after requirements grilling. Parent plan: `issue-623-625-music-photo-support-plan.md`, Phase 8. This frontend approval supersedes its frontend pause; backend exclusions remain.

## Scope and boundaries

- Full **applicable** Movie/TV parity, preserving existing Movie/TV behavior.
- Separate, recognizable family workflows. Movie/TV are references, not business workflows to invoke for Music, Photos or Other Videos. Existing shared transport, rendering and infrastructure may remain shared; no combined family business workflow.
- Music: artists → artist detail → expandable albums/discs/tracks, with selection/download at artist, album and track levels. Descendant detail API requests remain unsupported.
- Photos: albums → owned images/clips, with album/image selection. Photo-library clips remain Photos.
- Other Videos: individual overview/detail/selection. No folder or subtree explorer.
- Applicable search/filter/sort, table/poster modes, counts/icons/metadata, original choices, destinations, confirmation, queue/progress/history/lifecycle/realtime, translations and desktop/mobile behavior.
- Preserve existing selection lifetime and parallel family UX. No cross-library basket or new mixed-family product workflow. Do not redesign the established request envelope or existing Movie/TV coexistence.
- Original selectors retain MediaId/DataId semantics and existing fallback; no new mandatory-choice/cardinality rules or fabricated video quality for audio/photos.
- Music comparison is required, including applicable ownership/pending/partial presentation. Photos/Other Videos have no comparison badges, controls or filters. Audio-quality ranking/upgrades remain deferred.
- Independent server-persisted family view-mode and download-confirmation preferences are required. Do not borrow Movie/TV settings or add browser-local persistence as a substitute.
- No playback, lightbox/slideshow, new integration, destination/path redesign, live-data mutation, unrelated refactoring or automatic commits.
- Frontend-only edits. Necessary backend dependencies must be escalated; this approval does not authorize backend implementation.

## Verified prerequisites and upstream dependencies

- This worktree is indexed as `Reaparr-front-end-integration`; its ClientApp is available in WebStorm.
- Current comparison endpoint validates/dispatches Movie/TV only. The user reports Music comparison is being generated upstream; integrate its actual contracts when supplied. Do not invent APIs or claim runtime support before verification.
- Current backend display settings persist only Movie/TV view modes; confirmation settings persist only Movie/TV hierarchy switches. Required new-family settings must be supplied upstream before final acceptance.
- Use the TypeScript contracts generated by the user from this worktree's development backend; never hand-edit generated contracts or consume another checkout's Swagger. The user explicitly directed the assistant not to run the backend.
- Current Music detail DTO exposes albums/tracks and sort indexes, but no disc number/grouping metadata. Disc-aware rendering requires an upstream contract; do not invent groups from filenames or overload TV identifiers.

## Review gates

Implement one phase, report changed files/contracts, working behavior, diagnostics/tests/runtime evidence and blockers, then request approval before the next phase. No automatic commits. Keep incomplete later phases explicit; a phase pass is not full frontend completion.
