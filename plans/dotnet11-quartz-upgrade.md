# Quartz upgrade: Quartz 3.x → 4.8.1 (latest stable)

Status: **Reaparr uses Quartz 4.7.3 with published AppAny 0.6.2 plus a repository-owned EF model bridge; latest stable is Quartz 4.8.1.** The 4.8.1 NuGet release was published on 2026-11-21, and its package includes a `net11.0` asset with runtime async. Quartz says 4.7 applications compile on 4.8 unchanged; the 4.8 upgrade adds no Quartz database migration. Updating Quartz does not remove Reaparr's existing 3-to-4 migration or AppAny bridge.

**State and sequencing:** the user directed that BulkExtensions remain in use and its EF11 upgrade wait for upstream [PR #1971](https://github.com/borisdj/EFCore.BulkExtensions/pull/1971). That PR is open, not a published package. Keep Quartz at 4.7.3 until a stable EF11-compatible BulkExtensions package is available and the BulkExtensions callsites, version and locks are reconciled. After restoring the original reference and callsites, the targeted Data concurrency test run had 2 passes and 2 failures, reproducing the EF11 `MissingMethodException` and a rollback assertion failure after that bulk error. The persistence gate is not green. Run Quartz 4.8.1 compatibility checks only after that blocker is resolved and the Data baseline compiles; the upgrade's unrelated framework/API/frontend work may proceed independently. Docker and desktop smoke checks remain excluded by the user. No Quartz 4.8.1 Reaparr runtime verification has been run.

The existing `20261120215533_UpgradeQuartzSchema` migration consolidates two prior drafts into one EF-generated migration; its operations are not handwritten.

### 4.8.1 compatibility changes to prove before accepting the upgrade

Quartz 4.7 applications compile on 4.8 unchanged, and the upstream schema-change guide lists no 4.8 database migration. That does not establish Reaparr's runtime behavior. The Quartz 4.8 release notes and migration guide identify these changes that intersect current configuration:

- **Execution-history store is built when the scheduler is constructed.** A store that cannot be built now fails scheduler construction/startup; 4.7 could start and fail each history event instead. Reaparr enables history with `services.AddQuartzExecutionHistory(options => options.Retention = TimeSpan.FromDays(7))`, then calls `UseExecutionHistory()` on its persistent store. Keep `SQLiteDelegate` deriving from Quartz's `StdAdoDelegate`; verify the 4.8.1 history store resolves during scheduler construction with the configured Autofac-backed provider and 7-day retention. Preserve existing history data and verify terminal outcomes, summaries/redaction, expiry and job-status updates using the current SQLite fixture.
- **Container disposal shuts down any scheduler the container built.** Reaparr also owns explicit `Boot` → `BackgroundJobsSetup` shutdown and waits for background moves/download handling. Verify disposing both the actual application host and the isolated integration-test container does not introduce premature shutdown, duplicate stop, failure to await running jobs, or undisposed scoped job dependencies. Keep explicit host shutdown waiting behavior; Quartz's automatic disposal path is not a substitute for the existing ordered shutdown pipeline.
- **Recovery reports the original scheduled fire time and is not a misfire.** `GetRunningJobUpdates` currently maps Quartz's `FireInstance.ScheduledFireTimeUtc` to public `JobStatusUpdate.JobStartTime`. Add or adapt a focused regression for the recovered firing semantics that Reaparr consumes; if any handler treats scheduled time as actual fire time, use Quartz's documented `SchedulerConstants.FailedJobOriginalTriggerFireTime` for the original attempt instead. Ordinary, manual and startup-triggered behavior must remain unchanged.
- **4.8 adds an official `net11.0` Quartz asset using runtime async.** This is not a separate package requirement, but it changes the actual Quartz execution path under this solution's `net11.0` TFM. Verify Reaparr's async job/listener contracts, cancellation/interruption and shutdown under Quartz 4.8.1 on the .NET 11 runtime, not just compile-time API or the existing 4.7.3 / .NET 10 coverage.
- **.NET 11 ThreadPool behavior is a specific, unresolved runtime risk—not a correctness fix.** Quartz maintainers describe lower throughput and higher CPU for a bounded RAMJobStore/no-op-job workload on .NET 11.0.0, and cite `DOTNET_ThreadPool_SpuriousDispatchNoSpinThreshold=0` as a workaround. Reaparr uses persistent SQLite in production and RAMJobStore in parts of the test harness, so do not apply a process-wide setting preemptively. After Quartz 4.8.1 is in use and the test/build blocker is resolved, compare the repository's supported production and in-memory scheduler paths using an existing bounded performance harness if available. If none exists, do not create an ad-hoc harness without approval; report this performance risk as unverified. Apply a workaround only with Reaparr-specific evidence of material regression and an explicit scope decision.
- **AppAny mapping compatibility is still an independent gate.** AppAny 0.6.2's published README says its model covers Quartz 4.0, 4.2 and 4.3 additions; Reaparr's `QuartzSqliteSchema` supplies the 4.6/4.7 and execution-history/job-status fields. No AppAny 4.8.1 package metadata or 4.8.1-specific mapping evidence was found. Verify the generated model/snapshot and fresh plus prior-Reaparr migration fixture against the Quartz 4.8.1 runtime; do not remove the bridge or alter applied migrations just because Quartz 4.8 itself has no schema change.

**4.8.1 gate (blocked until the BulkExtensions EF11 release is available and targeted persistence tests pass):** on .NET 11, run `QuartzRuntimeIntegrationTests` against its fresh SQLite database and synthetic prior-Reaparr migration fixture; verify history-store construction/7-day retention, stored payload and paused-trigger preservation, job-scope release, cancellation and ordered shutdown. Add/extend a focused recovery-mapping regression for the `FireInstance` semantics consumed by `GetRunningJobUpdates`, preserving ordinary/manual/startup behavior. Then run the complete Application unit project and targeted Quartz backend integration cases. This existing fixture uses application migrations up to `20261031153443_AddMusicPhotosAndOtherVideos` before applying later migrations, so it is not a released-build database rehearsal. A package restore, `net11.0` asset, or 4.7.3 test result alone is not 4.8.1 evidence.

The application now uses Quartz 4 conventions, native `AddQuartz` through Autofac's service-provider bridge, its existing scoped registrations/listeners, and a repository-owned EF schema/migration. The following checklist describes the migration completed to reach Quartz 4.7.3, not work still pending for the 4.8.1 package step.

## Decision and current contracts

1. **Latest stable target: Quartz 4.8.1** (NuGet V3 index checked 2026-11-22; current manifest/lockfile resolve Quartz 4.7.3). Update the direct Quartz package and lockfile only after the focused 4.8.1 gate passes. The current all-direct-ID NuGet inventory finds Quartz as the sole direct package behind latest stable; it is intentionally deferred until the user-directed BulkExtensions EF11 gate is green. Transitive package patch status is tracked separately in the dependency inventory and is not implied by this direct-package statement.
2. **`Autofac.Extras.Quartz` is absent from current project files and locks and must remain absent.** Its latest stable 11.0.0 requires Quartz `[3.16.1,4.0.0)`; Reaparr already uses native `AddQuartz` through the Autofac-backed service-provider factory.
3. Preserve the existing Autofac bridge, per-job scoped registrations, listener setup boundary and single DI job factory. Do not add a second factory, scheduler instance or hosted-service shutdown owner.
4. Preserve one host-owned lifecycle pipeline: `Boot` → `BackgroundJobsSetup`. Keep the outer move/download shutdown order, local-fire cancellation, 30-second stop deadline and wait-for-jobs behavior. Verify Quartz 4.8 container disposal does not prematurely stop the scheduler or skip the application-owned pipeline.
5. Preserve production SQLite, the `QRTZ_` table prefix, typed System.Text.Json JobDataMap values (`StoreJobDataAsStrings=false`), per-connection PRAGMAs, five-minute misfire threshold, two-minute database retry interval, schema validation and seven-day history retention. EF migration must complete before persistent scheduler construction/resolution; `SchemaProvisioning.Validate` is not a migration.
