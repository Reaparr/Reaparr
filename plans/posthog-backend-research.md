# PostHog .NET backend research

Event research was checked on 2026-10-31; PostHog Logs and Serilog OTLP guidance on 2026-11-01. The selected implementation uses a lean injectable `ITelemetry` event interface backed by the official core PostHog .NET SDK `2.18.1`, the current telemetry ID returned by `IUserService.GetTelemetryId`, and the existing standard Serilog OTLP log path. The SDK owns normal event queueing, batching, retries, and disposal flush; Reaparr adds no custom event transport or lifecycle. There is no telemetry settings module or mutation API. The [implementation handoff](posthog-maintainer-runbook.md) owns the current scope and contracts. Earlier direct Capture API/no-queue wording is explicitly superseded below. Regression coverage alignment is pending the final parent result; this research is not proof of current source verification.

## Package and minimum integration

- **Documented and selected:** PostHog publishes `PostHog` (core) and `PostHog.AspNetCore` (ASP.NET Core conveniences). The ASP.NET Core setup registers the client as a singleton with `builder.AddPostHog()`; the core package can be registered with `services.AddPostHog()` or constructed as a singleton. Use the documented core services registration as a normal singleton and inject `IPostHogClient` into `Reaparr.Application.Telemetry`. The SDK uses an internal asynchronous queue and `/batch`; `Capture` is intentionally non-blocking. [ .NET SDK docs ](https://posthog.com/docs/libraries/dotnet)
- **Documented vendor defaults:** The default ingestion host is `https://us.i.posthog.com`; an EU project uses `https://eu.i.posthog.com`. Reaparr does not lock to either host: build-time `TelemetryHost` accepts a validated absolute HTTPS origin with an optional port and optional single trailing slash. `ProjectToken` identifies the project. The selected SDK options retain their defaults for `Disabled=false`, `IsServer=true`, `FlushAt=100`, `FlushInterval=5s`, `MaxBatchSize=100`, `MaxQueueSize=10,000`, `MaxRetries=3`, and compression enabled. The bounded in-memory channel uses `DropOldest` when full. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Config/PostHogOptions.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** `Capture(...)` returns only whether the SDK accepted an event into its sending queue (`true`/`false`), not whether PostHog accepted, ingested, or delivered it. `FlushAsync()` has no delivery result. The public `IPostHogClient` surface has `Capture`, `FlushAsync`, `Dispose`/`DisposeAsync`, but no queue-clear/discard operation. The selected implementation does not call `FlushAsync` per event. [`IPostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/IPostHogClient.cs)
- **Documented:** Automatic exception capture is not available in the .NET SDK. PostHog Logs uses OpenTelemetry rather than this analytics SDK, so the existing Serilog OTLP sink remains the Logs path. Manual `Capture` calls do not implicitly export application errors or logs. [ .NET SDK docs ](https://posthog.com/docs/libraries/dotnet)
- **Selected version:** use the explicitly pinned `PostHog` **2.18.1** package. The reviewed package repository revision is `761bd01094f420027e1450390948a72519507116`; do not float the package or substitute the obsolete `2.18.0` research note.

## Credentials: project token versus personal API key

- **Documented:** PostHog's `/i/v0/e` and `/batch` are public POST-only ingestion endpoints. They use the project token and do not return sensitive project data. A project token is therefore the only credential needed for event capture. [API overview](https://posthog.com/docs/api), [Capture and batch API](https://posthog.com/docs/api/capture)
- **Documented:** Personal API keys authenticate private `GET`/`POST`/`PATCH`/`DELETE` API calls, can provide account-like access, must remain private, and must not be used in frontend code. [Personal API keys](https://posthog.com/docs/api/personal-api-keys)
- **Documented:** Current .NET options call the privileged value `SecretKey`; it accepts a personal API key (`phx_...`) or project secret API key (`phs_...`). The old `PersonalApiKey` property is an obsolete alias. It is used for local feature-flag definitions/remote config, not ordinary event capture. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Config/PostHogOptions.cs), [`PostHogApiClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Api/PostHogApiClient.cs)
- **Selected credentials:** the public project token and embedded ingestion origin configure the core SDK for events and the existing PostHog OTLP log path. No personal/project-secret key goes into Docker/desktop build inputs, artifacts, runtime settings, or frontend code.

## Enrichment and privacy defaults

- **Documented:** The .NET SDK deliberately disregards the server IP, does not add GeoIP properties, and does not use server GeoIP for flag evaluation. Captured events receive SDK metadata (`$lib`, `$lib_version`), a generated UUID, the event's `distinct_id`, and `$geoip_disable=true`; the default `IsServer=true` adds `$is_server=true`. These SDK-owned fields are expected and are not an exact raw API-schema contract. [`CapturedEvent.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Api/CapturedEvent.cs), [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/PostHogClient.cs), [GeoIP section of .NET docs](https://posthog.com/docs/libraries/dotnet#geoip-properties)
- **Documented/optional:** `PostHog.AspNetCore` request-context middleware is not required for capture. If enabled, it reads client-controlled PostHog tracing headers and adds request metadata including `$current_url`, `$request_method`, `$request_path`, `$user_agent`, and `$ip`; explicit IDs/properties override it. [Request context docs](https://posthog.com/docs/libraries/dotnet#request-context)
- **Selected event boundary:** use the core .NET SDK, but no request-context middleware and no browser PostHog SDK. The diagnostic is the first caller of injected `ITelemetry`; events carry the current telemetry ID returned by `IUserService.GetTelemetryId` plus allowlisted parameters/common metadata and the approved person/GeoIP privacy properties. Do not forward client IPs, request headers, cookies, URLs, or browser context. Names, email, Plex data, and exceptions remain outside the event payload. The existing Serilog path exports broader operational messages/properties/exception details using its approved `IsUnmasked` behavior.

## Flush, shutdown, retries, and acknowledgement limits

- **Documented:** The SDK flushes periodically and at `FlushAt`; `FlushAsync()` drains all queued events. During `DisposeAsync()`, the SDK stops background loops and then deliberately performs a final flush of remaining items. [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/PostHogClient.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** Batch requests retry network/transport failures and HTTP 408, 429, and 5xx responses, up to `MaxRetries` (default 3) with exponential backoff. A batch is dequeued before its send; a failed send is logged by the async handler and is not exposed as a per-event result or automatically re-enqueued. [`HttpClientExtensions.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Library/HttpClientExtensions.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** PostHog's HTTP `200` means the payload was received in the correct format and the project token was valid; it does **not** prove that each event was valid or ingested. Events missing a name or `distinct_id` can still receive `200` and not be ingested. The SDK's `ApiResult` models only a coarse status (`{"status":"Ok"}` for batch), while `FlushAsync()` does not return it. [API responses](https://posthog.com/docs/api#responses), [invalid events](https://posthog.com/docs/api/capture#invalid-events), [`ApiResult.cs`](https://github.com/PostHog/posthog-dotnet/blob/761bd01094f420027e1450390948a72519507116/src/PostHog/Api/ApiResult.cs)
- **Recommendation:** Treat capture as best-effort telemetry. Use the SDK's boolean only as queue-admission status, never retry in application code based on it, and do not describe `Capture`, `FlushAsync()`, SDK retries, or HTTP `200` as proof of ingestion or delivery.

## Selected event lifecycle

- The selected core SDK owns the asynchronous queue, batching, normal retries, background lifecycle, and disposal flush. `Capture` is non-blocking; `true` means the SDK accepted the event for sending and `false` means queue-admission failure. Reaparr adds no custom event transport, fallback, queue, retry, or per-event flush.
- SDK-owned upstream failures after queue admission are asynchronous and are not a synchronous `TrackAsync`/HTTP `503` promise for future batch sends. A `503` remains appropriate for unavailable build configuration or queue-admission failure; do not promise a safe lookup-failure `503` or add adapter-side UUID validation.
- Operational logs use the existing standard Serilog OTLP path and attach immediately when immutable build configuration is valid, without a settings-loaded admission gate or bootstrap replay. Their severity follows the global logger threshold, masking follows `IsUnmasked`, file/Seq sinks remain available when telemetry is unconfigured, and SignalR attaches without rebuilding the logger.

## Selected minimum implementation

1. Add one provider-neutral `ITelemetry.TrackAsync(eventName, parameters)` in the Domain contract boundary and one Application `Telemetry` implementation in `Reaparr.Application.Telemetry`. Its first consumer is the diagnostic endpoint, which uses ordinary authenticated access without an explicit admin-role or principal-name check; do not create a forwarding-only command, separate sender, or unrelated instrumentation.
2. Register the pinned core `PostHog` `2.18.1` client normally as a singleton and inject `IPostHogClient` into `Telemetry`. Keep common fields, reserved keys, the telemetry ID, and privacy properties in the implementation; call the non-obsolete `Capture` overload with `groups: null` and `flags: null`. Every event resolves the current telemetry ID through `IUserService.GetTelemetryId`, regardless of authentication mode or owning use case; callers cannot supply an identity. Do not add adapter-side UUID validation or promise a safe lookup-failure `503`.
3. Configure the standard Serilog OTLP sink directly in `LogConfig` with the existing `IsUnmasked`-controlled sensitive-data behavior and ordinary Serilog shutdown/disposal. Attach remote OTLP immediately on configured builds without settings admission; follow the global logger threshold, preserve file/Seq sinks when unconfigured, and attach SignalR without rebuilding the logger. No custom sink, sanitizer, wrapper, transport, or lifecycle classes. Verify Logs separately from SDK event acceptance.

## Settled decisions and verification boundaries

- Events use the SDK's normal queue, batching, retries, background lifecycle, and disposal flush; an event cannot be retracted after SDK acceptance. Reaparr adds no custom queue, retry, fallback, per-event flush, or queue-purge lifecycle. Logs use bounded standard batching and may flush accepted records during shutdown.
- The official core `PostHog` `2.18.1` event SDK and existing Serilog OTLP log path are selected. The earlier direct-event/no-queue design is superseded; `2.18.1` is a dependency to use, not a package to reject. Retain the existing Serilog sink/configuration unchanged.
- Always reuse the current telemetry ID returned by `IUserService.GetTelemetryId`, not a principal identifier, caller-supplied UUID, or separate installation identity. Resolve it for every event, equally with normal authentication, development authentication bypass, and background consumers; do not change the bypass setting or require login for this lookup. Do not add adapter-side UUID validation or promise a safe lookup-failure `503`. Account recreation or a copied authentication database follows the existing identity lifecycle; no telemetry-specific identity migration, generation, or cache is required.
- `TelemetryHost`/`TelemetryProjectToken` are build-time constants without runtime overrides. A region/token change requires a new build; no privileged keys are supplied to these builds.
- Project IP storage remains enabled (`anonymize_ips: false`), as selected during live setup on 2026-11-01. Keep the SDK's documented `$geoip_disable: true` behavior and do not forward end-user IP headers; retaining ingestion-source IPs does not authorize additional client-IP collection.
- UI/API status must say **Diagnostic event accepted for sending** when the SDK admits the event. It must not claim HTTP acceptance, ingestion, or delivery. Live verification requires observing the correct telemetry ID, origin, release, and trigger time in PostHog.

## Selected Serilog/PostHog Logs integration

- PostHog documents `https://us.i.posthog.com/i/v1/logs` with OTLP HTTP/Protobuf and `Authorization: Bearer <project token>`. Reaparr derives the equivalent `/i/v1/logs` path from configured `TelemetryHost`; this documented US URL is a vendor example, not an application host allowlist. The same public ingestion credential is used for events and logs, not a personal key. The documentation's Microsoft `ILogger` provider example is not a requirement to replace the existing Serilog pipeline ([PostHog .NET Logs](https://posthog.com/docs/logs/installation/dotnet)).
- `Serilog.Sinks.OpenTelemetry` maps existing Serilog messages, properties, and exception details to OTLP records. Configure it directly in `LogConfig`; no analytics event SDK or additional logging provider is required ([first-party sink documentation](https://github.com/serilog/serilog-sinks-opentelemetry)).
- The sink documentation describes `ignoreEnvironment: true`, explicit `LogsEndpoint`, `HttpProtobuf`, embedded authorization, and traces/resource settings; these are vendor facts for the existing approved Logs path, not new event-SDK work. Do not route Logs through `IPostHogClient` or add an advanced settings/toggle/API surface ([first-party documentation](https://github.com/serilog/serilog-sinks-opentelemetry/blob/dev/README.md), [configuration reference](https://github.com/serilog/serilog-sinks-opentelemetry/blob/dev/_autodocs/configuration.md)).
- **Approved minimal masking policy:** use the existing sensitive-data behavior controlled by `IsUnmasked`: mask when it is false and retain unmasked values when it is true. It masks configured properties and recognized email/URL values when enabled, but does not guarantee redaction of exception text or all free-text credentials and paths. The maintainer explicitly selected this tradeoff instead of maintaining custom sanitization.
- `SignalRLogConfig.AttachSignalR` must attach to the existing logger without rebuilding or replaying it. Configured builds attach the standard OTLP sink immediately without a settings-loaded admission gate or bootstrap replay; severity follows the global logger threshold, file/Seq sinks remain available when telemetry is unconfigured, and Serilog owns batching, failure isolation, and disposal flush. Do not add another logging owner or lifecycle.
