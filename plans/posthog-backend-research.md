# PostHog .NET backend research

Event research was checked on 2026-10-31; PostHog Logs and Serilog OTLP guidance on 2026-11-01. Annotation review selected a lean injectable `ITelemetry` event interface backed by the Capture API, existing login account UUIDs for event identity, `advancedSettings.telemetryDisabled`, and automatic masked Information+ Serilog log export. Event requests remain unqueued; previously accepted log batches may drain after opt-out. The [implementation handoff](posthog-maintainer-runbook.md) owns the current scope and contracts.

## Package and minimum integration

- **Documented:** PostHog publishes two relevant packages: `PostHog` (core) and `PostHog.AspNetCore` (ASP.NET Core conveniences). The ASP.NET Core setup registers the client as a singleton with `builder.AddPostHog()`. The core package can be registered with `services.AddPostHog()` or constructed as a singleton. The SDK uses an internal asynchronous queue and `/batch`; `Capture` is intentionally non-blocking. [ .NET SDK docs ](https://posthog.com/docs/libraries/dotnet)
- **Documented:** The default ingestion host is `https://us.i.posthog.com`; an EU project uses `https://eu.i.posthog.com`. `ProjectToken` identifies the project. The current options source defaults `Disabled=false`, `IsServer=true`, `FlushAt=100`, `FlushInterval=5s`, `MaxBatchSize=100`, `MaxQueueSize=10,000`, `MaxRetries=3`, and compression enabled. The bounded in-memory channel uses `DropOldest` when full. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Config/PostHogOptions.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** `Capture(...)` returns only whether an event was enqueued (`true`/`false`), not whether PostHog accepted or ingested it. `FlushAsync()` has no delivery result. The public `IPostHogClient` surface has `Capture`, `FlushAsync`, `Dispose`/`DisposeAsync`, but no queue-clear/discard operation. [`IPostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/IPostHogClient.cs)
- **Documented:** Automatic exception capture is not available in the .NET SDK. PostHog Logs uses OpenTelemetry rather than this SDK. Therefore manual `Capture` calls do not implicitly export application errors or logs unless Reaparr adds those integrations. [ .NET SDK docs ](https://posthog.com/docs/libraries/dotnet)
- **Version advice:** NuGet currently lists `PostHog` **2.18.0**, published 2026-10-29. Use an explicitly reviewed/pinned version (and lock transitive dependencies) rather than a floating version; compatibility still needs to be checked against Reaparr's target framework. [NuGet package](https://www.nuget.org/packages/PostHog)

## Credentials: project token versus personal API key

- **Documented:** PostHog's `/i/v0/e` and `/batch` are public POST-only ingestion endpoints. They use the project token and do not return sensitive project data. A project token is therefore the only credential needed for event capture. [API overview](https://posthog.com/docs/api), [Capture and batch API](https://posthog.com/docs/api/capture)
- **Documented:** Personal API keys authenticate private `GET`/`POST`/`PATCH`/`DELETE` API calls, can provide account-like access, must remain private, and must not be used in frontend code. [Personal API keys](https://posthog.com/docs/api/personal-api-keys)
- **Documented:** Current .NET options call the privileged value `SecretKey`; it accepts a personal API key (`phx_...`) or project secret API key (`phs_...`). The old `PersonalApiKey` property is an obsolete alias. It is used for local feature-flag definitions/remote config, not ordinary event capture. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Config/PostHogOptions.cs), [`PostHogApiClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Api/PostHogApiClient.cs)
- **Selected credentials:** the public project token and embedded ingestion origin authenticate Capture API events and PostHog OTLP logs. No personal/project-secret key goes into Docker/desktop build inputs, artifacts, runtime settings, or frontend code.

## Enrichment and privacy defaults

- **Documented:** The .NET SDK deliberately disregards the server IP, does not add GeoIP properties, and does not use server GeoIP for flag evaluation. Captured events receive SDK metadata (`$lib`, `$lib_version`), a generated UUID, the event's `distinct_id`, and `$geoip_disable=true`; the default `IsServer=true` adds `$is_server=true`. [`CapturedEvent.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Api/CapturedEvent.cs), [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/PostHogClient.cs), [GeoIP section of .NET docs](https://posthog.com/docs/libraries/dotnet#geoip-properties)
- **Documented/optional:** `PostHog.AspNetCore` request-context middleware is not required for capture. If enabled, it reads client-controlled PostHog tracing headers and adds request metadata including `$current_url`, `$request_method`, `$request_path`, `$user_agent`, and `$ip`; explicit IDs/properties override it. [Request context docs](https://posthog.com/docs/libraries/dotnet#request-context)
- **Selected event boundary:** no request-context middleware or PostHog event SDK. The diagnostic is the first caller of injected `ITelemetry`; events carry the existing account UUID plus allowlisted parameters/common metadata, `$process_person_profile: false`, and `$geoip_disable: true`. Names, email, Plex data, headers, and exceptions remain outside the event payload. The separately approved Serilog path exports broader masked messages/properties/exception details.

## Flush, shutdown, retries, and acknowledgement limits

- **Documented:** The SDK flushes periodically and at `FlushAt`; `FlushAsync()` drains all queued events. During `DisposeAsync()`, the SDK stops background loops and then deliberately performs a final flush of remaining items. [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/PostHogClient.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** Batch requests retry network/transport failures and HTTP 408, 429, and 5xx responses, up to `MaxRetries` (default 3) with exponential backoff. A batch is dequeued before its send; a failed send is logged by the async handler and is not exposed as a per-event result or automatically re-enqueued. [`HttpClientExtensions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Library/HttpClientExtensions.cs), [`AsyncBatchHandler.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Library/AsyncBatchHandler.cs)
- **Documented:** PostHog's HTTP `200` means the payload was received in the correct format and the project token was valid; it does **not** prove that each event was valid or ingested. Events missing a name or `distinct_id` can still receive `200` and not be ingested. The SDK's `ApiResult` models only a coarse status (`{"status":"Ok"}` for batch), while `FlushAsync()` does not return it. [API responses](https://posthog.com/docs/api#responses), [invalid events](https://posthog.com/docs/api/capture#invalid-events), [`ApiResult.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Api/ApiResult.cs)
- **Recommendation:** Treat capture as best-effort telemetry. Keep PostHog work off the request's correctness path, never retry it in application code based on `Capture`'s boolean, and do not describe `FlushAsync()` or HTTP `200` as proof of ingestion.

## Opt-out/discard conflict

- **Documented:** `PostHogOptions.Disabled` defaults to `false` and is read once when `PostHogClient` is constructed; changing it after activation has no effect. Disabled capture is a no-op, but the option does not expose a way to clear an already populated queue. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Config/PostHogOptions.cs), [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/PostHogClient.cs)
- **Event-path conflict:** direct events retain the strict no-unsent-queue policy. The PostHog SDK lacks public queue discard, and disposal final-flushes; batch calls use `CancellationToken.None`. This remains a reason to use direct Capture API requests for events. It is not the selected policy for logs: the user explicitly permits standard Serilog batches accepted before opt-out to drain. [`IPostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/IPostHogClient.cs), [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/PostHogClient.cs)
- **Partial mitigation only:** `PostHogOptions.BeforeSend` is called after enrichment and before serialization; returning `null` drops that event. A callback that reads a shared opt-out flag can drop queued items when they reach a flush, but it is not an atomic queue purge and cannot retract an item whose batch has already been serialized/sent. [`PostHogOptions.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/Config/PostHogOptions.cs), [`PostHogClient.cs`](https://github.com/PostHog/posthog-dotnet/blob/main/src/PostHog/PostHogClient.cs)
- **Verdict and selected resolution:** the current public .NET SDK cannot guarantee that every unsent SDK-queued event is discarded at opt-out. Use direct single-event Capture API requests with no queue or retries instead; gate dispatch on the current instance-wide opt-out state. Requests already dispatched cannot be retracted reliably.

## Selected minimum implementation

1. Add one provider-neutral `ITelemetry.TrackAsync(eventName, accountUuid, parameters, cancellationToken)` in the Domain contract boundary and one Application `PostHogTelemetry` implementation. Its first consumer is the diagnostic handler; do not create a separate sender or instrument unrelated use cases now.
2. Keep event submission at one Capture API request, without SDK queue/retries. Common fields and reserved keys belong to the implementation, not callers. HTTP diagnostic identity is resolved server-side; background consumers must supply an explicit trusted existing account context.
3. Persist instance opt-out in the minimal AdvancedSettings module and expose its control on Settings → Advanced. The debug page contains proof actions/status only.
4. Add the standard Serilog OTLP sink for masked Information+ operational logs, using the same embedded host/token, independent remote masking, admission filtering, and permitted pre-opt-out drain. Keep both paths non-fatal and verify Logs separately from events.

## Settled decisions and verification boundaries

- Events have no retry/queue state and cannot retract dispatched requests. Log opt-out stops new admission but permits standard pre-opt-out batches to drain; no custom purge lifecycle is required.
- The direct event interface and Serilog OTLP log path are selected. NuGet 2.18.0 above concerns the unused PostHog event SDK, not a dependency to add. The Serilog sink version must be reviewed/pinned against the project's existing Serilog package.
- Reuse the existing authenticated login account UUID, not a separate installation identity. Account recreation or a copied authentication database follows the existing identity lifecycle; no telemetry-specific identity migration or generation is required.
- Host/token are build-time constants without runtime overrides. A region/token change requires a new build; no privileged keys are supplied to these builds.
- UI/API status must distinguish submitted/accepted from remotely observed delivery. Live acceptance requires observing the correct account UUID, origin, release, and trigger time in PostHog.

## Verified Serilog/PostHog Logs integration

- PostHog documents `https://us.i.posthog.com/i/v1/logs` with OTLP HTTP/Protobuf and `Authorization: Bearer <project token>`. This is the same public ingestion credential used for events, not a personal key. Its documentation's Microsoft `ILogger` provider example is not a requirement to replace an existing Serilog pipeline ([PostHog .NET Logs](https://posthog.com/docs/logs/installation/dotnet)).
- `Serilog.Sinks.OpenTelemetry` maps existing Serilog messages, properties, and exception details to OTLP records, without requiring the OpenTelemetry SDK. It can be added as one branch of Reaparr's existing logging setup ([first-party sink documentation](https://github.com/serilog/serilog-sinks-opentelemetry)).
- Programmatic Serilog sink configuration is overridable by runtime OTEL variables unless `ignoreEnvironment: true` is specified. Use that setting, an explicit `LogsEndpoint`, `HttpProtobuf`, embedded authorization, traces disabled, and approved build resource labels ([first-party documentation](https://github.com/serilog/serilog-sinks-opentelemetry/blob/dev/README.md), [configuration reference](https://github.com/serilog/serilog-sinks-opentelemetry/blob/dev/_autodocs/configuration.md)).
- Source mapping includes `Exception.Message`/`Exception.ToString()` as exception attributes, so masking only named structured properties cannot sanitize exception text. Prepare a separately sanitized remote representation and never let local `IsUnmasked` disable its redaction. Broad masked logs are best-effort redaction, not a guarantee of no residual personal/media data.
- Repository evidence: `LogConfig` currently bypasses masking under `IsUnmasked`, and `SignalRLogConfig.AttachSignalR` rebuilds the logger. Activation must wait for persisted settings, preserve a single exporter owner across rebuilds, and avoid duplicate export/bootstrap replay. These are implementation constraints, not observed PostHog delivery.
