# Reaparr .NET 11 + latest stable NuGet implementation plan

**Status:** implementation is in progress. The .NET 10 package migration and Quartz 4.7.3 cutover have been completed, and the shared target, SDK pin, supported RID publication configuration, CI and Docker metadata have been retargeted to .NET 11. The latest stable Quartz is 4.8.1, intentionally deferred per the user's sequencing decision until a stable EF Core 11-compatible BulkExtensions package is released and targeted persistence tests pass. The target migration is not accepted as complete until remaining framework/runtime, package, persistence and consumer-behavior gates pass. Current SDK: 11.0.100. See the [package ledger](dotnet11-dependency-inventory.md#implemented-package-batches-on-net-10) for historical package-batch evidence and the [Quartz 4.8.1 gate](dotnet11-quartz-upgrade.md#481-compatibility-changes-to-prove-before-accepting-the-upgrade).

## Scope and acceptance

Target .NET 11, C# 15, and the latest compatible stable versions of all direct dependencies and the resolved transitive dependency graph; replace libraries that cannot support the runtime. A package is only “latest stable” when both the feed version and its role/constraints in every project lockfile have been checked; version selection is not compatibility proof. Quartz 4.8.1 is latest stable but intentionally deferred until the user-directed stable EF11-compatible BulkExtensions release and passing persistence gate. Acceptance remains backend unit/integration suites, real API generation and client checks, persistent SQLite migration/query/download behavior, telemetry, update/package contracts, multiarchitecture Docker and all six desktop targets. Docker builds and desktop smoke tests are intentionally excluded from this pass at the user's request; they remain unverified release gates, not claims of success.

The current NuGet.org direct-package inventory (2026-11-22) covers all 75 distinct direct package IDs across 41 PackageReference projects; Quartz 4.7.3 is the sole direct package behind latest stable (4.8.1), intentionally deferred by the user's sequencing decision. A scoped primary-source review also found Microsoft.OpenApi 3.11.0 in the current transitive lock graph, behind 3.11.1; see the [dependency inventory](dotnet11-dependency-inventory.md#current-stable-version-audit-2026-11-22) and its transitive compatibility notes. Resolve/verify the OpenAPI patch during the net11 API gate. PackageReference versions are lower bounds; use selected lock versions for actual resolution. This snapshot is not a claim that every transitive package is latest.

The implementation baseline is commit `184b07619`, which contains the accepted PR #721 memory-ownership fixes. The checkout has not switched branch, committed, or published.

### 3. Framework/runtime correctness gates — unresolved

**Restore and final dependency resolution:** four redundant direct package references identified by NU1510 were removed without suppression; regenerated lockfiles passed `dotnet restore Reaparr.sln --locked-mode --verbosity quiet`. The 2026-11-22 direct-package inventory covers all 75 distinct direct IDs; Quartz 4.8.1 remains the single intentional exception (not latest-stable compliant until its user-directed gate passes). The full resolved package graph audit is still a required acceptance step: compare every selected package in each project's lockfile with the latest stable version allowed by its dependency constraints, record intentional pins/conflicts, and update/relock where compatible. A known transitive gap is Microsoft.OpenApi 3.11.0 vs upstream 3.11.1; resolve and verify it with the .NET 11 OpenAPI gate. Also inspect EF10/Extensions 10.0.x minimum edges from FlexQuery, AppAny and BulkExtensions; lock unification and successful restore do not establish runtime compatibility.

- **Quartz/AppAny — waiting behind the selected BulkExtensions gate:** Quartz 4.8.1 is latest stable, but the user-directed BulkExtensions EF11 update is not yet published. Keep Quartz at 4.7.3 until a stable EF11-compatible BulkExtensions release is available, the source/package graph restores and compiles, and targeted persistence tests pass. Then apply the [focused Quartz 4.8.1 compatibility gate](dotnet11-quartz-upgrade.md#481-compatibility-changes-to-prove-before-accepting-the-upgrade). Quartz 4.8 adds no upstream database migration, but Reaparr's existing `20261120215533_UpgradeQuartzSchema` migration and `QuartzSqliteSchema` bridge cover the known 4.7.3 model; complete Quartz 4.8.1/EF11 model/runtime compatibility is unverified. AppAny 0.6.2 documents Quartz 4.0/4.2/4.3 mapping and an EF10 dependency group. Keep applied migrations intact, preserve scheduler/history state, and validate EF's model/snapshot and fresh plus prior-Reaparr migration fixtures.
- **Bulk/range persistence — blocked by reproduced EF11 package incompatibility:** BulkExtensions remains the chosen persistence path. Its direct `EFCore.BulkExtensions.SQLite` reference is 10.0.1 and the current package/lock graph still resolves 10.0.1 under EF Core 11. Upstream [PR #1971](https://github.com/borisdj/EFCore.BulkExtensions/pull/1971) remains open and proposes an EF11 build. After restoring the original reference and callsites, `ReaparrDbContextConcurrencyUnitTests` ran on .NET 11: 2 passed and 2 failed. The contending bulk-write case fails with the upstream-reported `MissingMethodException`; the rollback case fails its expected-exception assertion after that bulk failure. Keep the existing bulk callsites/configuration and wait for an upstream stable EF11 package; do not replace the API with native range methods. Once released, update version/locks and rerun the Data class, affected persistence/media-sync tests, then the broader suites. The regression contract requires generated IDs, detached updates and tracked-instance identity/value coherence, update-not-upsert for unknown keys, cancellation, rollback and target-row preservation.
- **FlexQuery:** direct version 4.0.0 is latest stable but its lock resolves EF Core 10.0.0 alongside the direct EF11 package. Exercise current overview/search callers under EF11 and assert returned data; package minimum metadata and restore do not prove runtime behavior.
- **EF11 API changes:** `ShouldFailClosedWhenNoMigrationsAreFound` pins direct EF11 `Migrate()` behavior. Verify it and the existing fail-closed setup path. EF11 split-query concurrency behavior changed; no deterministic SQLite test seam was identified. Exercise the download hierarchy caller under concurrent modification only if a deterministic repository-level seam exists.
- **SQLite:** lockfiles unify SQLitePCLRaw core/provider/bundle at 3.0.5 and native SQLite at 3.54.1, but historical EF10 dependency edges name 2.1.13. EF11 declares 3.0.5. Verify exact runtime assets and native loading; the earlier .NET 10 `SELECT 1` test is not .NET 11/RID evidence.
- **Runtime compatibility unknowns:** System.Reactive 7.0, Velopack 1.2.161, PostHog, OpenTelemetry, Serilog, FlexQuery 4.0, FastEndpoints 9 and Testably helpers have not all been exercised end-to-end on net11. Their asset groups are version/TFM evidence only; the inventory records the source-backed package-family scope and remaining gaps.

- **Transitive OpenAPI patch:** the current net11 OpenAPI lock graph resolves Microsoft.OpenApi 3.11.0; upstream 3.11.1 fixes copy-constructor preservation of document extensions/tags and reader allocation. Review and resolve this transitive patch while rebuilding the .NET 11 OpenAPI/client gate; do not leave it implicit in the FastEndpoints upgrade. After host start, capture internal/public OpenAPI (FastEndpoints 9 uses 3.2 by default on net11), verify representative schemas and API-versioning behavior, regenerate the client, and run frontend typecheck/contract tests. The historical .NET 10 OpenAPI 3.1.1 result does not prove net11 output or Swagger UI rendering.
- **Testing/coverage:** TUnit 1.87.12 declares net11 assets and carries MTP coverage/TRX dependencies, but no net11 full-suite run establishes discovery, hooks, coverage option behavior, nonempty Cobertura or multi-project output separation. Gate full backend tests and verify actual coverage artifacts after the BulkExtensions prerequisite is resolved; no claim of net11 coverage acceptance from restore/asset metadata.
- **Polly adapter coexistence:** direct Polly/Polly.Core 8.9.1 coexist with `Microsoft.Extensions.Http.Polly` 11.0.0 resolving Polly 7.2.4/Polly.Extensions.Http 3.0.0 in AppHost. - **Downloader/runtime boundaries:** run persisted resume/cancel/failure-recovery tests and real callback lifecycle under net11. In particular, a resumed single-segment response where the server ignores Range is rejected by Downloader rather than appended at the saved offset; do not add a new retry path absent approval. Confirm the disk-space budget when a short resume artifact requires restart. The user's acceptance includes downloads/resume/cancel, so this boundary must be explicitly accepted or demonstrated before calling the download contract complete.
- **Telemetry and updater:** PostHog/OpenTelemetry/Serilog end-to-end delivery, Velopack installed old-version→download→apply→restart, and native desktop runtime support remain unverified. Velopack has net8/net9/net10 assets but no net11-specific group; this is not itself a failure. Docker/desktop smoke evidence remains excluded from this pass, so retain that as an explicit unverified release gate.

**Build/runtime gate — blocked by the reproduced BulkExtensions EF11 incompatibility:** SDK 11 and earlier locked-restore/compilation evidence exist but are not acceptance. This is not a complete .NET 11 backend test pass. Keep BulkExtensions pending a stable EF11 package as directed; do not substitute native EF APIs. The earlier `CS0246` build error was caused by unauthorized removal of the dependency, and duplicate-key failures were from the unauthorized native-range implementation; neither is current source behavior.
